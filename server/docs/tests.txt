📚 Plan de Pruebas Maestro — Módulo de Upload (NestJS + Clean Architecture)

Fecha: 09-Oct-2025 (America/Bogotá) • Versión del plan: 1.0 • SDET responsable: Principal SDET (15+ años)

Objetivo: Garantizar corrección funcional, seguridad, resiliencia e histogramas de rendimiento del Módulo de Upload para habilitar su despliegue confiable en producción. El plan sigue la pirámide de pruebas, cubre todas las capas de la arquitectura limpia y aplica técnicas avanzadas (property-based, fuzzing y mutación).

0) Resumen Ejecutivo

Pilares:

Correctitud (reglas de dominio y casos de uso),

Contrato API (DTOs, validaciones, respuestas, errores),

Integración real (PostgreSQL + Azurite/Azure),

Seguridad (API key, validaciones defensivas),

Rendimiento (P95/P99, throughput, costo DB),

Resiliencia (fallos intermitentes de Azure/DB/Transacciones).

Entornos:

Unit: aislado (sin IO).

Integration: Testcontainers (PostgreSQL), Azurite (o cuenta de prueba Azure).

E2E: Nest e2e app + Validación exhaustiva de HTTP.

Performance: k6/Artillery.

Security: fuzz de DTOs + pruebas de validadores personalizados.

Cobertura objetivo:

Domain: ≥ 95% líneas / 100% reglas críticas.

Application (use cases): ≥ 90%.

Infra adapters: ≥ 80% (límites por IO).

HTTP/E2E (contratos): ≥ 90% (rutas y variantes).

Mutación (StrykerJS): Mutation Score ≥ 75% global; ≥ 90% en entidades de dominio.

Property-Based (fast-check) — Dominio

Objetivo: explorar espacios de entrada grandes validando invariantes.

Ej. FileProperties.sizeInBytes >= 0, md5Hash null | 32-hex.

Ej. UploadItem nunca llega a VERIFIED si no pasa por UPLOADED.

Ejemplo (pseudo-código):

import * as fc from 'fast-check';

it('UploadItem no puede saltar directamente a VERIFIED', () => {
  fc.assert(
    fc.property(fc.record({
      // generar combinaciones de estados previos
    }), (rec) => {
      const item = makeUploadItem({ status: rec.start });
      // intentar verify() en estados ≠ UPLOADED -> siempre lanza
      if (rec.start !== 'UPLOADED') {
        expect(() => item.verify('a'.repeat(32))).toThrow();
      }
    })
  );
});

6) E2E (HTTP) — Contrato API

App creada con @nestjs/testing, ValidationPipe global, ApiKeyGuard habilitado, AllExceptionsFilter activo. Headers: x-internal-secret.

6.1 POST /api/upload/sessions

Happy Path (E2E-POST-SESS-001)

Precondiciones: DB limpia; header API key válido.

Body: CreateUploadSessionDto válido con 1..N files.

Pasos: POST.

Esperado: 201; JSON con sessionId, status=OPEN, items PENDING, blobName formato correcto.

Validaciones (400)

domain fuera de enum → 400 (E2E-VAL-DOM-001)

clientBatchId no UUID → 400 (E2E-VAL-UUID-001)

files vacío → 400 (E2E-VAL-MIN-001)

fileName con ../ o \ o non-ASCII → 400 (E2E-VAL-FN-001..003)

fileSizeBytes <= 0 → 400 (E2E-VAL-SIZE-001)

contentType fuera de whitelist → 400 (E2E-VAL-MIME-001)

md5 no 32-hex → 400 (E2E-VAL-MD5-001)

Auth

Falta header → 401 (E2E-AUTH-KEY-001)

Header incorrecto / valor inválido → 401 (E2E-AUTH-KEY-002/003)

Idempotencia

Misma clientBatchId + domain con sesión OPEN previa → 201 con misma sessionId (E2E-POST-SESS-IDEM-001).

6.2 POST /api/upload/sessions/:sessionId/sas-batch

200 con sas[] y expiresOn (E2E-SAS-001).

404 si sesión no existe (E2E-SAS-404-SES-001).

404 si blobName ajeno (E2E-SAS-404-ITM-001).

400 si DTO inválido (E2E-SAS-400-001).

401 sin/erróneo API key.

6.3 POST /api/upload/sessions/:sessionId/sas/refresh

Igual a /sas-batch (E2E-SAS-REF-001..).

6.4 POST /api/upload/sessions/:sessionId/complete

Happy Path (verify=true, failOnIncomplete=false)

Simulación: subir blobs a Azurite con size/md5 correctos → 200; finalStatus=COMPLETED; conteos ok (E2E-COM-HPY-001).

Escenarios

verifyAndPromote=false → no consulta metadata; completa (E2E-COM-NV-001).

failOnIncomplete=true con un fallo → finalStatus=FAILED (E2E-COM-FLG-001).

onlyClientItems → procesa subset, el resto sin cambios (E2E-COM-SUB-001).

MD5 mismatch / blob inexistente → item FAILED; resumen coherente (E2E-COM-MD5-001 / E2E-COM-404-BLOB-001).

Formato de error en 400/404 conserva {status, code, message, details, traceId, timestamp, path, method} (E2E-ERR-FMT-001).

7) Seguridad
7.1 Fuzzing (DTOs y validadores)

Objetivo: descubrir bypasses de validación, DoS por payloads grandes, codificaciones inesperadas.

Superficies:

fileName (path traversal ../, UTF-8 malformado, null bytes, overlong, emojis, homoglyphs).

blobName (segmentos excesivos, longitud > 1024).

contentType (MIME extraño image/jpég, image/../../jpeg).

md5 (longitudes variadas, no hex, mayúsculas/minúsculas inconsistentes).

Arrays items muy grandes (límite razonable + 10%).

Ejecución:

Fuzzer ligero con fast-check generando payloads y esperando 400 consistente.

Inyección de null bytes y overlong UTF-8 (usa buffers y toString('utf8') controlado).

Casos:

SEC-FUZ-DTO-001..020 (varias permutaciones por campo).

SEC-PATH-TRAV-001: ../../../etc/passwd en fileName → 400.

SEC-ENC-001: Unicode confusables (\u202E, bidi) → 400.

SEC-SIZE-ARR-001: items con 10k entradas → 400 o 413 (si configurado a nivel gateway).

7.2 Autenticación (API Key)

Variantes: header ausente, header alterno, valor vacío, valor incorrecto → 401 (E2E-AUTH-KEY-001..004).

7.3 Otras (estáticas/dinámicas)

SAST/Dependencias: npm audit, eslint-plugin-security (no bloqueantes pero informativas).

Headers de seguridad delegados a gateway (documentado en scope).

8) Rendimiento y Resiliencia
8.1 Metas (SLA objetivo, HW de CI)

Create Session: P95 < 200 ms, P99 < 350 ms (N ≤ 20 files).

SAS Batch (≤100 items): P95 < 150 ms (Azul/Azurite local).

Complete (N≤100, verify=true): P95 < 500 ms (metadata en cache Azurite).

8.2 Cargas (k6/Artillery)

Escenarios:

100 usuarios concurrentes: ciclo crear sesión → sas-batch (10 items).

40 rps sostenidos sobre /sas-batch (TTLs cortos).

/complete con 100 items (50 correctos, 50 fallos MD5).

KPIs: latencias P50/P95/P99, rps, errores, CPU/Heap (Node), tiempos de transacción DB.

Reglas de fail (thresholds): si P95 supera SLA por 5 min → fail.

Nota: para complete realista, pre-seed blobs en Azurite con MD5 calculado.

8.3 Resiliencia / Fault Injection

Azure fallos transitorios: simular ECONNRESET, timeouts → APP-COM-AZR-001; E2E-COM-AZR-TMO-001.

DB contention: crear sesiones en paralelo con mismo clientBatchId → INF-DB-IDX-001 y RES-RACE-CRS-001 (sólo una insert).

Transacción fallida: forzar excepción a mitad (inserta sesión, falla al insertar items) → rollback consistente.

10) Casos de Prueba Detallados (muestrario ampliado)

A continuación, especificaciones concretas (Descripción / Precondiciones / Pasos / Resultado) para los flujos principales.
Nota: las variantes y combinaciones se amplían en suites dedicadas.

10.1 Create Upload Session — Happy Path (E2E-POST-SESS-001)

Descripción: Crea sesión con un archivo válido.

Precondiciones: DB limpia; INTERNAL_API_SECRET correcto; Azurite corriendo (no requerido para este endpoint).

Pasos:

POST /api/upload/sessions con body válido (domain=plant, clientBatchId v4, files[0] con fileName seguro, fileSizeBytes>0, contentType whitelisted, md5 válido opcional).

Esperado:

HTTP 201.

status=OPEN, items[].status=PENDING.

blobName con patrón {domain}/{timestamp}/{clientItemId}/{fileName}.

Campos obligatorios presentes (fechas ISO), sin null indebidos.

10.2 Create Upload Session — Idempotencia (E2E-POST-SESS-IDEM-001)

Precondiciones: Sesión OPEN existente para clientBatchId+domain.

Pasos: repetir POST con mismo clientBatchId y mismo set de files.

Esperado: 201 con misma sessionId; no duplica ni items ni sesiones.

10.3 SAS Batch — item inexistente (E2E-SAS-404-ITM-001)

Precondiciones: Sesión creada con un blobName A; pedir SAS para blobName B.

Pasos: POST /sas-batch con item B.

Esperado: 404 con code acorde (ej. ITEM_NOT_FOUND) y formato de error estándar.

10.4 Complete Session — Verify OK (E2E-COM-HPY-001)

Precondiciones:

Sesión con N items; en Azurite existen blobs correspondientes con size/md5 correctos.

verifyAndPromote=true (por defecto). failOnIncomplete=false.

Pasos: POST /complete.

Esperado:

200; cada item en VERIFIED; finalStatus=COMPLETED.

summary.verified=N, incomplete=0, failed=0, total=N.

10.5 Complete Session — MD5 mismatch + failOnIncomplete=true (E2E-COM-FLG-001)

Precondiciones: Al menos un blob con MD5 no coincidente.

Pasos: POST /complete con failOnIncomplete=true.

Esperado: items fallidos FAILED; finalStatus=FAILED; summary.failed>=1.

10.6 Complete Session — Subset (E2E-COM-SUB-001)

Precondiciones: N items; proveer onlyClientItems con subset.

Pasos: POST /complete con subset.

Esperado: solo esos items cambian; el resto mantiene su estado inicial.

11) Property-Based & Fuzz — especificación

Asserts:

13) Riesgos y Mitigaciones
Riesgo	Impacto	Mitigación

Azure intermitente (timeouts)	Falsos fallos en complete	Retries con backoff (si se define), marcar FAILED y respetar failOnIncomplete
